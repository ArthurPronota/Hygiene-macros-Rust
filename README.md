# Гигиена макросов в Rust: разбор твоего примера

Твой пример — минимальная и очень наглядная демонстрация гигиены:

```rust
macro_rules! my_once {
    () => { let x = 1; let _ = x; };
}

fn main() {
    let mut x = 10;
    my_once!();              // внутри свой x = 1
    println!("x: {}", x);    // 10 — внешний x не тронут
}
```

```
x: 10
```

Если бы макрос **не был** гигиеничным, `let x = 1;` внутри transcriber'а перекрыл бы внешний `x`, и `println!` вывел бы `1`. В C-макросах именно так и происходит — и это источник классических багов.

## Что такое гигиена

**Гигиена** — свойство макроса, при котором идентификаторы, созданные **внутри** макроса, не конфликтуют с идентификаторами **снаружи** и наоборот.

Формально: каждый идентификатор несёт **контекст синтаксиса** (syntax context) — откуда он пришёл: из кода пользователя или из transcriber'а макроса. Два `x` с разными контекстами — это **разные** идентификаторы, даже если пишутся одинаково.

```
Внешний x:  контекст вызова
Внутренний x: контекст макроса
              ↓
        это разные x
```

## Три уровня гигиены в `macro_rules!`

Гигиена в Rust **не полная** — она работает по-разному для разных видов идентификаторов.

### 1. Локальные переменные — **полная гигиена** ✅

```rust
macro_rules! m {
    () => { let x = 1; let _ = x; };
}

fn main() {
    let x = 10;
    m!();
    println!("{}", x);   // 10 — свой x у макроса
}
```

Имена, **созданные** внутри transcriber'а, не видны снаружи и не перекрывают внешние. Это работает и в обратную сторону:

```rust
macro_rules! m {
    () => { let y = x + 1; };   // ← x берётся из контекста вызова?
}

fn main() {
    let x = 10;
    m!();                        // ❌ ошибка: cannot find value `x`
}
```

Внутри макроса `x` **не виден**, даже если снаружи есть `x` — потому что `x` в transcriber'е имеет контекст макроса, а не вызова. Это защищает от случайного захвата внешних имён.

### 2. Имена, переданные **снаружи** — сохраняют свой контекст ✅

```rust
macro_rules! m {
    ($e:expr) => { let $e = 1; };  // ❌ не скомпилируется
}
```

А вот так — работает:

```rust
macro_rules! m {
    ($name:ident) => { let $name = 1; };
}

fn main() {
    m!(x);          // создаёт x в контексте вызова
    println!("{}", x);  // 1 — x виден снаружи!
}
```

Идентификатор `$name`, переданный **извне**, сохраняет контекст вызова. Поэтому `x`, созданный через `$name`, виден в `main`. Это важно: макрос может **намеренно** создавать переменные в контексте вызывающего, если пользователь передал имя.

### 3. Типы, трейты, функции — **не полная гигиена** ⚠️

```rust
macro_rules! m {
    () => {
        let v: Vec<i32> = Vec::new();   // ← какой Vec?
    };
}
```

Здесь `Vec` **не гигиеничен**: он разрешается в контексте вызова. Если пользователь определил свой `Vec` в области видимости — макрос использует **его**, а не `std::vec::Vec`. Это классическая проблема.

Именно поэтому в макросах, экспортируемых из библиотек, пишут:

```rust
macro_rules! m {
    () => {
        let v: $crate::Vec<i32> = $crate::Vec::new();
    };
}
```

`$crate` — специальная метапеременная, которая **всегда** указывает на крейт, где **определён** макрос, а не где он **вызван**. Это «ручная гигиена» для путей.

## `$crate` — главный инструмент борьбы с не-гигиеной

```rust
// В библиотеке my_lib:
#[macro_export]
macro_rules! make_vec {
    () => {
        // ❌ плохо: Vec может быть переопределён у пользователя
        Vec::new()

        // ✅ хорошо: всегда std::vec::Vec из крейта определения
        // (через $crate::... или ::std::vec::Vec)
    };
}
```

Два способа:

1. **`$crate::path::to::Item`** — путь относительно крейта-определения.
2. **`::std::vec::Vec`** — абсолютный путь (ведущий `::`), не зависит от локальных `use`.

Оба защищают от «теневых» имён у вызывающего.

## Почему в C всё иначе

В C макрос — это **текстовая подстановка** до компиляции. Никакого контекста нет:

```c
#define ONCE() { int x = 1; (void)x; }

void f(void) {
    int x = 10;
    ONCE();          // разворачивается в { int x = 1; (void)x; }
    printf("%d\n", x);  // 10 — но только потому, что внутренний x в своём блоке
}
```

В C спасают фигурные скобки (создают новую область видимости), но стоит убрать их — и `x` перекроет внешний:

```c
#define BAD() int x = 1;
void f(void) {
    int x = 10;
    BAD();            // int x = 1; ← ошибка: redeclaration
    printf("%d\n", x);
}
```

Rust-гигиена убирает **целый класс** таких багов: не нужно думать о «свободных» именах внутри макроса, не нужно придумывать префиксы вроде `MYLIB_INTERNAL_x`.

## Границы гигиены: сводка

| Что | Гигиенично? | Пример |
|-----|-------------|--------|
| Локальные `let`-переменные внутри transcriber'а | ✅ да | `let x = 1;` не конфликтует с внешним `x` |
| Имена, переданные через `$ident` | сохраняют контекст вызова | `m!(x)` создаёт `x` в контексте вызова |
| Типы, трейты, функции, макросы | ⚠️ нет | `Vec` разрешается в контексте вызова |
| Пути (`foo::bar`) | ⚠️ нет | нужно `$crate::foo::bar` |
| Лейблы (`'label`) | ⚠️ нет (исторически) | — |
| `$crate` | ✅ всегда на крейт-определение | — |

## Практические правила

1. **Экспортируемый макрос** → используй `$crate::` для всех путей к своему крейту и `::std::...` для стандартной библиотеки.
2. **Внутренние имена** в transcriber'е — можно не префиксовать, гигиена защитит.
3. **Имена, которые макрос должен создать в контексте вызова** — передавай через `$ident`.
4. **Не полагайся на гигиену для типов** — она не работает; используй полные пути.
5. **Тестируй макрос в «враждебном» окружении** — определи `Vec`, `String`, `Result` в тестовом модуле и убедись, что макрос не ломается.

## Итог

- Гигиена — это разделение контекстов идентификаторов: внутренние имена макроса не видны снаружи и не захватывают внешние.
- В Rust **локальные переменные** полностью гигиеничны; **типы, трейты, пути** — нет.
- `$crate` — инструмент ручной гигиены для путей: всегда указывает на крейт-определение.
- Твой `my_once!` демонстрирует **полную гигиену локальных имён**: `x` внутри макроса не перекрывает `x` в `main`, поэтому вывод `x: 10`.
- Это устраняет класс багов, типичных для C-макросов, но **не отменяет** необходимости `$crate::` для экспортируемых макросов.
